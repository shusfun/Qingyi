# 0001 翻译输入的段落重建规则由轻译与 mistral-gui 共享

## 背景

用户从 PDF、截图或网页上复制的文字，常常在句子中间带硬换行。如果按每个换行切开分别翻译，模型拿到的是残句，译文既不通顺，也会多花请求。

mistral-gui 的粘贴翻译和截图翻译要处理这个问题；轻译的划词翻译在选中跨行文字时也会遇到。两边如果各写一套规则，同一段文字在两处的合并结果会不一样。

## 决定

翻译前先重建段落，轻译和 mistral-gui 使用同一套规则：

- 空行是段落分隔。
- 同一段内的单个换行合并成一行：
  - 拉丁文字之间补一个空格，中日韩文字直接相连；
  - 行尾是连字符、下一行以小写字母开头时，去掉连字符直接相连。
- 以下情况保留换行，不合并：
  - 下一行以列表符号开头，如 `1.`、`-`、`•`、`(a)`；
  - 上一行是很短的标题行；
  - 行看起来是代码或表格。
- 规则中的参数放在 `source/shared/translation-rules.json`，包括列表符号模式、标题长度阈值、连字符规则；轻译仓库是唯一来源，通过现有同步脚本复制到 mistral-gui。
- 算法在 TS（轻译）和 Go（mistral-gui）中各实现一遍，用同一组样例输入和期望输出测试，保证两边结果一致。
- 用户可以看到合并后的原文并修改，也可以切换为「按原换行逐行翻译」，用于诗歌、代码、表格等每行独立的内容。

mistral-gui 侧的分段与展示方式见 mistral-gui 仓库的 `docs/decisions/0001-粘贴与截图翻译的分段与展示.md`。

## 考虑过的方案

- **按每个换行逐行翻译（mistral-gui 原来的做法）**：PDF 和截图中被硬换行截断的句子会被拆成残句分别翻译，质量差。放弃。
- **完全照搬百度翻译的合并方式**：2026-11-18 实测百度在线翻译，它在段内合并换行、按空行分段，效果好；但会把列表项也并成一行（「1. … 2. …」挤在同一行），丢失列表结构。所以参考它的思路，补上列表、标题、代码的例外。
- **只在 mistral-gui 实现**：划词时跨行选中的文字同样有换行问题；两边规则不一致，用户会在两处看到不同结果。放弃。
- **把整个算法写成数据驱动的通用规则**：没有必要。只共享参数和样例，算法两边各写一遍，更简单也更好测。

## 影响

- 共享规则文件和同步检查的覆盖范围扩大到段落重建参数，改规则时两边会一起变。
- 两边都要维护同一组样例测试；新增例外规则时，先补样例。
- 合并改变了送去翻译的文本，可能影响缓存命中：合并后的段落是新的缓存键，这是预期的行为。

## 依据

- 2026-11-18 与用户的讨论。用户选择「智能合并段落也参考百度呀」，划词翻译选择「套用，规则共享」。
- 同日实测百度翻译文本翻译页：段内硬换行被合并，空行分段，有「段落对照」视图；列表项被合并到同一行。
- 原实现：mistral-gui `internal/app/translate.go` 的 `splitDesktopParagraphs` 按每个 `\n` 切分。
